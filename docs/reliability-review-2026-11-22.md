# 全量 Review 与可靠性修复（2026-11-22）

本轮从上一轮已合并的 `28a1702` 开始，分支为 `codex/reliability-review-20261122`。对网页、扩展、API、认证、上传、任务消费、checkpoint、转写/检索/Agent、媒体工具和发布配置重新做入口及调用链检查，深入验证共享状态、失败补偿和资源生命周期。保留现有产品功能、数据结构、依赖及 Google Java Format/Prettier/架构检查规则。

以下只列出能说明具体触发条件并落实修复的问题。范围检查不等于形式化证明所有代码、外部服务或故障组合均不存在问题。

## 修复与依据

| 级别 | 触发条件和影响 | 最终处理及回归 |
| --- | --- | --- |
| P1 | 分片已经登记，重试请求仍在替换该对象时，另一个请求开始合并。原先两者没有共同的锁，合并可能读取变更中的分片版本，清理结束后迟到上传又创建临时对象。 | 上传持有 uploadId 对应的共享读锁，合并持有同一把读写锁的写锁；并行分片仍可同时进入。锁内再次读取完成回执。两个线程验证在途上传阻止合并，上传结束后可完成；另外模拟锁等待期间完成上传，验证迟到请求不写入分片及索引。 |
| P1 | Broker 或缓存复用任务很快，消费者在发送调用返回前已经发出 COMPLETED；投递服务随后才发送 QUEUED，状态倒退，订阅者可能一直等待不存在的新完成事件。管理员重放具有相同问题。 | 在发送 MQ 前发布排队事件，发送失败则发布 DISPATCH_FAILED 终态。通知失败继续派发，已经发送的消息不因通知错误伪装为失败。回归明确构造 MQ 返回前完成的情况，检查普通任务、重放的事件顺序和派发失败路径。 |
| P1 | MySQL 用户名使用不区分大小写的比较，而登录失败的 Redis key 保留输入大小写。同一账号可通过变换字母大小写重新获得失败次数额度。 | 仅失败计数 key 按 `Locale.ROOT` 转小写，用户名展示、数据库查询和会话规则保持原行为。交替大小写的第 9 次失败尝试返回 429，成功清理使用同一 key；验证短密码旧账号仍可登录并升级哈希。 |
| P2 | 登录失败 INCR 成功后、设置 EXPIRE 前发生故障，会留下没有 TTL 的失败计数，账号可能长期被限流。 | Redis Lua 将递增和设置过期合并为原子操作；同时修复已有无 TTL 的计数。使用原有 10 分钟窗口，不引入新限流政策。回归检查使用单次脚本调用及 600 秒参数；本轮没有真实 Redis 故障注入。 |
| P2 | 排队中的 ASR/OCR Future 被取消时，Callable 不会运行，其 finally 中的 CountDownLatch 不会递减。构建流程会等待后判定分支未结束并保留临时目录。 | 使用完成计数受控的 `BranchTask`：取消尚未运行的任务立即计数；正在运行的任务必须真正退出后才计数。回归覆盖排队取消、重复取消、运行中不响应中断的工作，以及正常/异常退出，防止提前删除仍在使用的目录。 |
| P2 | 服务退出时，原生工具只在单次 run 的 finally 中回收；Bean 销毁没有阻止新启动或主动终止仍在运行的工具。 | 记录当前执行器持有的进程，启动登记与关闭状态使用同一临界区。`@PreDestroy` 关闭准入并终止仍持有的进程；每个 run 继续释放容量。真实 Java 子进程验证关闭后 PID 已退出、调用返回非零并拒绝新工作；这不代表强制杀死 JVM 时仍能执行关闭回调。 |
| P2 | 初次查询媒体的数据库调用位于 try/finally 外。数据库抛异常时，trace 未 flush/clear，线程池复用后可能残留前一个任务的上下文。 | 查询纳入统一异常和清理路径。媒体不存在时不重新创建失败 checkpoint。回归分别覆盖查询异常和已删除媒体，确认 flush/clear 均执行。 |
| P2 | 失败台账追踪异常的最底层 cause 时，仅防御直接自引用；两个异常互相引用会形成无限循环，占住消费者线程。 | 与其他异常分类路径一致，将 cause 遍历限制为 16 层。构造真实双向 cause 环，验证台账记录按时完成且仍保留错误类型与原因。 |
| P2 | `audio_%03d.mp3` 只是最小位数，编号 1000 会在字典序中排到 101 前；使用列表位置计算时间还会在分片缺失时把后续语音提前。 | 过滤实际音频分片并按文件中的数字编号排序，以原编号计算时间戳。测试使用 099、100、101、1000 和非音频文件，验证排序、稀疏时间轴和调用数量。 |
| P2 | 同一媒体按新计划重跑时，旧证据搜索只比较 mediaId 和搜索计数，仍可能写入新工作区；会话变化但工作区尚未重置时也存在旧响应写入。 | 新分析/修订开始时使旧搜索失效并释放忙碌状态；搜索回调同时核对工作区版本、认证会话及请求身份。延迟响应回归验证同媒体修订和认证变化后旧证据不写回。 |

登录服务还补齐了与现有 HTTP DTO 相同的 128 字密码上限；该项是服务层一致性保护，原有 HTTP 入口本来已有限制，不将其描述为新发现的远程漏洞。

## 部署与保留边界

分片与合并改用共同的读写锁，键为 `lock:upload:state:<uploadId>`。部署时应排空旧 API 实例的在途上传/合并请求再协调切换，避免旧实例仍使用旧合并锁而新实例使用读写锁。数据库、上传对象名、元数据、完成回执和现有会话 key 不变；无需数据库迁移，也不应删除已有上传数据。大小写不同的旧失败计数按原 TTL 到期，新请求使用统一计数 key。

每个在途分片增加 Redis 读锁操作，换取合并与写入的一致性；不同分片仍可并行。此次优化侧重避免错误顺序、重复失败和资源残留，不声称每条路径的延迟都降低。

本轮锁回归使用模拟 Redisson 对象与真实本地读写锁，Redis Lua 通过调用契约测试验证；尚未进行真实 Redis/MQ/数据库/对象存储/向量服务的多实例压力及故障测试，也未调用真实 ASR/LLM。媒体进程生命周期使用真实 Java 子进程，长音频用编号文件模拟，不声称完成数十小时真实视频的识别质量评估。UI 改动限于异步响应状态，使用延迟请求回归，没有新增样式或操作流程。

未引入跨数据库、缓存、MQ 和对象存储的统一事务/outbox，也没有新增持久 SSE 日志或全局恰好一次保证。对象清理、上传会话过期后的临时对象生命周期、在途删除和历史存储权限仍需要部署及存储策略配合。强制退出进程、网络隔离和外部服务配额属于运行环境边界。
