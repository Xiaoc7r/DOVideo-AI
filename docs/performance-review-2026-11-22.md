# 性能与代码治理记录（2026-11-22）

基线为 `421dcd2`，分支为 `codex/performance-governance-20261121`。目标是保留既有上传、转写、分析、修订、追问、证据检索、导出及扩展功能，减少重复计算与资源争用，并让代码规范可以在 CI 中持续检查。预期使用场景是个人或小团队在一台开发机/单实例服务上运行长视频任务；更高负载通过队列和显式容量预算处理。

采用用户指定的 [Ponytail](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md) 原则：先追踪调用与数据流、复用现有库和平台能力、只引入解决实际问题的抽象。审查覆盖媒体入口、消息消费、上下文/分块/检索、checkpoint/列表缓存、模型与原生工具调用、网页工作区、扩展和 CI 配置。保留上一轮修复及后续证据类型校验。

## 已落实的改动

| 原问题 | 修改与验证 |
| --- | --- |
| 每个五分钟窗口重新扫描全部片段，空白时间跨度也逐窗循环。 | 排序后使用游标一次收集每个实际存在的窗口。分区扫描由 O(窗口数 × 片段数) 降为 O(片段数)，排序仍为 O(n log n)。回归覆盖乱序、空值、窗口边界、大时间间隔、摘要/Embedding 失败降级，原始证据不变。 |
| 不同分析目标与证据检索同时遇到分块缓存缺失，会重复调用摘要和 Embedding。 | 分块按媒体记录获取 Redisson 共享锁，锁内重新检查 checkpoint；成功后只保存/索引一次。等待最多 30 秒且受 Agent 剩余时间约束。并发测试使用两个线程验证只构建和索引一次，失败不缓存，预算耗尽后释放锁。 |
| MQ 使用依赖的默认消费线程数，原生 FFmpeg/OCR 由不同类直接启动，整体资源开销难控制。 | MQ 生命周期中同时设置最小/最大线程，默认 2；媒体工具统一通过 `MediaProcessRunner`，默认最多 2 个顶层进程，受控 FFmpeg 的输入、输出和滤镜线程设为 1，OCR 通过 `OMP_THREAD_LIMIT=1` 限制 OpenMP。下载器也参与进程准入，但它自行产生的子进程线程数仍取决于工具自身行为。 |
| 工具等待、超时、中断和进程终止处理分散。 | 共享执行器统一处理最多 30 秒准入等待、总截止时间、异常和中断回收；繁忙时返回可识别的 503 业务错误。清理存活子进程，再回收父进程和容量。ASR/OCR 循环检查中断，避免取消后继续发起下一段昂贵工作。测试覆盖互斥、线程环境、排队拒绝、启动失败、超时、中断及之后的容量恢复。 |
| 自建线程池的核心线程在空闲后仍保留。 | 启用核心线程超时回收，保留原有有界队列、拒绝策略和关闭语义。活动期间容量未按 CPU 数无限扩张。 |
| 分析接口仅检查媒体归属，却从数据库取出整份转写与分析正文；消费存活检查也取整行。 | 分析控制器使用专门的轻量元数据读取，保留同一归属检查；存活检查使用 exists 查询。测试验证投影不包含 `transcript_text`、`ai_summary`，不存在/越权仍拒绝。需要正文的转写接口继续读取正文。 |
| 普通状态查询每次尝试读取通常不存在的修订 checkpoint，同一请求还重复读取活跃状态。 | 先取一次活跃状态，仅活跃任务查询待应用修订。已完成任务省去修订缺失时的数据库回源；Redis 异常时按原有边界读取非待修订的持久结果，不伪造未知任务或修订完成。 |
| checkpoint 的 payload 和 stage 分两次 HSET 写入，有额外往返和部分字段可见窗口。 | 使用单次 Hash `putAll` 写入同一组字段，再设置 TTL；保留数据库事务、提交后更新缓存和失败失效处理。测试验证同次写入以及旧字段回填不会倒退当前阶段。它不提供数据库与 Redis 的跨存储原子性。 |
| 资料卡片内嵌在整个 App 的渲染函数中，计时/输入更新会再次构建列表卡片；每张卡片多次线性搜索活动任务。 | 提取 `MediaCard.vue`，通过稳定 props 和事件隔离展示；活动任务预先构成 Map，保留第一个匹配任务的原有规则。卡片样式、状态、按钮、删除反馈和移动端规则跟随组件。 |
| 大段 JSON/文本没有应用层压缩。 | 启用 2KB 以上 JSON/文本响应压缩；不包含 SSE 和已压缩媒体，保留进度实时传输。未测量生产反向代理下的传输收益，部署时与代理配置共同核对。 |

资源预算均为每个后端实例的限制。`ANALYSIS_WORKER_CONCURRENCY=2` 替代当前依赖注解默认的 20 个消费线程；这减少同时进入昂贵流水线的工作，并非对整机 CPU 使用率的实测百分比。`MEDIA_MAX_PROCESSES=2`、`MEDIA_PROCESS_THREADS=1` 可以按机器容量调整。限制可能增加重负载时的排队时间，不降低音频质量、抽帧规则、图片分辨率或 Agent 分析要求。

## 代码与文件治理

所有 Java 源码和测试统一采用 Google Java Format（通过固定版本 Spotless），网页/扩展的 JS、Vue、CSS、HTML 和 JSON 采用固定版本 Prettier。EditorConfig/Git 属性统一编码、缩进和换行。CI 执行 Maven `verify` 与前端格式检查；四条 ArchUnit 规则约束控制器访问、下层反向依赖、数据类型与构造器注入。

`MediaProcessRunner` 合并了五处实际重复的进程控制职责；`MediaCard` 是具有独立数据与更新周期的展示组件。保留现有分层和模式策略，没有为了模式数量新增无用途的接口或工厂。具体职责与维护命令见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

基线有 172 个 Git 文件，已排除 `node_modules`、`target`、`dist` 和运行用配置。扫描后删除 `server/HELP.md`（未引用的 Spring 初始化帮助模板）、`docs/images/agent-result.png`、`docs/images/video-agent-demo.png`（未引用截图），共约 102KB；有引用的项目截图、审查记录、测试、迁移和 Maven Wrapper 保留。新增文件对应资源执行器、组件、回归测试、持续格式配置和维护记录，因此文件总数不会作为删减目标。Git 历史保留，删除资源可追溯恢复。

## 未验证的边界

本机 Docker 引擎未启动，未运行真实 Redis/RocketMQ/MySQL/MinIO/Qdrant 的多进程或全链路压力测试，也未调用真实 ASR/LLM。实际 Tesseract 未安装，OCR 原生命令的线程限制通过子进程环境回归验证；没有真实中文 OCR 质量对照。没有生产 CPU/RSS、长视频端到端时延、真实移动设备或 Core Web Vitals 数据，不能承诺任意规模并发下资源占用不变。

已有消息与持久化恢复机制继续沿用。跨 MySQL、Redis、对象存储和 MQ 的全局恰好一次、持久事件重放及删除与在途任务之间的所有竞争仍属于架构边界，本轮没有伪称消除这些问题。多实例部署要同时考虑外部服务配额和进程数总预算。
